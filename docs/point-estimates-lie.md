# 指标涨了,然后呢?

> 一份评估报告应该回答的不是「哪个数字更大」,而是
> **「这个差别是真的吗?我该不该动手?」**
>
> 这篇讲的是把前者换成后者需要补上的东西。所有例子和数据都来自一个真实项目
> (一个符号积分求解系统的评估),包括我自己在评估代码里踩的坑。

---

## 一、一个看起来没问题的报告

一个 56 道题的评估集,跑完之后报告是这样写的:

```
求解率        56/56    (100.0%)
top-1 方法族命中  55/56    (98.2%)
与标注闭式一致    51/51    (100.0%)
```

三个数字都很好看,而且**都没有区间**。

问题出在第一个:如果给 `56/56` 配一个教科书上的 Wald 区间
`p̂ ± z√(p̂(1−p̂)/n)`,因为 `p̂ = 1`,`(1−p̂) = 0`,**整个区间的宽度就是 0**。

于是报告实际上在说:

> 求解率 = 100% ± 0

这不是"很好",这是把**"我没测出问题"**说成了**"没有问题"**。

换成 Wilson 得分区间是 `[93.6%, 100%]` —— 这才是一句诚实的话,而且它在
面试里能被追问得住:"你们 56 道题全对,那真实水平的下界大概在哪?"
"93.6%" 是个能答的答案,"100%" 不是。

**任何比率都应该带区间,尤其是全对和全错的时候。** 这两种恰恰是 Wald 区间
完全失效、而项目里最常见的情形。

---

## 二、配对,而不是两组独立样本

假设你要比较改动前后的两个版本。最自然的做法是:各跑一遍,拿到两个比率,
做个比例检验。

**这是把手上最贵的那部分信息扔了。**

同一道题在两个版本上的难度是一样的。改动只影响"这道题被解出来的概率"这个
偏差项,而题目本身的难度是共同项。把它配掉之后,要检出的差异只来自改动本身,
噪音小得多。

所以应该用 **McNemar 检验** —— 它只看**分歧对**:改前错改后对的有多少道,
改前对改后错的有多少道。两版都对、两版都错的题,不提供关于"哪个版本更好"
的任何信息。

这个选择直接影响你需要多少样本,而且差距很大。

---

## 三、结论有三种,不是两种

这是整件事里最实用的一条。真实数据:

| 指标 | 改前 → 改后 | 分歧对 | 精确 p | 结论 |
|---|---|---|---|---|
| 求解 / 给出答案 | 70.0% → 90.0% | 16 | **0.0042** | 显著改善 |
| top-1 方法族命中 | 83.3% → 91.7% | 5 | 0.0625 | 证据不足 |
| top-1 卡片命中 | 66.7% → 66.7% | 0 | 1.0000 | 逐题相同 |

第二个和第三个**必须**说成不同的话:

* **逐题相同** = 两版在每一道题上结果都一样,**没有差异**。
  样本再多也没用,因为它根本不存在。
* **证据不足** = 观察到了差异,但**没测出来**是不是真的。
  扩样本可能有救。

如果报告把它们都印成"不显著",读者会去扩样本 —— 而这对第一种情况
**完全是白花钱**。这不是措辞问题,是决策问题。

## 四、一次报六个指标,就别怪有一个是假的

一次报 6 个指标、每个都用 α = 0.05,那么"至少有一个假阳性"的概率是

```
1 − 0.95⁶ ≈ 26%
```

四分之一。而这还只是 6 个。

所以对同一批指标**必须一起做多重比较校正**。上面的例子里,`p = 0.0042` 裸看很
漂亮,报 3 个指标做 Holm 校正后变成 `0.0125` —— 仍然显著,但门槛确实被抬高了。

Holm(强控制 FWER,对外下结论用)和 BH(控制 FDR,探索性分析用)是两个不同
的工具,别混用:前者说"这批结论里一个假的都不许有",后者说"允许少量假的,
但比例要受控"。

## 五、一个反直觉的推论:扩大评估集不提高判别力

这一条我第一次算出来的时候不太相信。

McNemar 精确检验**以分歧对的数量为条件**。也就是说,检验的判别力取决于
"两版表现不同的题有多少道",**而不是总题量**。

推论:

> 把评估集从 60 题扩到 200 题,如果新增的 140 道题两版表现都一样,
> **检出能力一点都不会提高**。

而扩评估集是标注成本最高的一件事。

在 60 道题的规模下,净改善至少要 **6 道**才可能被判为显著(最好情形:
改进全部集中在一个方向)。这个门槛和总题量几乎无关,只被总题量"封顶"。

所以标注预算该往哪花,答案很清楚:**补那些两版确实会分歧的题**。
盲目地把题量堆上去,买到的只是一份更长的、结论一样的报告。

## 六、最容易忽略的一条:你的评估代码本身也会错

这一段是自我批评。

上面所有分析都依赖一份逐题结果 JSON。而在我给这个项目加统计层的时候,发现
仓库里已经提交的报告文件里,有这样一个矛盾:

```
summary :  "value_match": 51      ← 汇总说 51 道全对
records :  逐题 value_match 为 True 的:0 道
```

**两个数字直接互相矛盾**,而报告本身看起来一切正常。

根因很蠢:写逐题记录的那段代码是

```python
record.update({
    "ok": bool(report.ok),
    ...
    "value_match": None if divergent else record.get("ok", False) and not value_note,
})
```

`record.get("ok", False)` 读的是**这次 `update` 之前**的字典 —— `"ok"` 还没写进去,
所以永远拿到默认值 `False`。于是逐题字段恒为 `False`,而汇总那边是单独累加的,
一直是对的。

**为什么这个 bug 危险:**

汇总数字是对的,报告看起来正常,但下游任何按题分析(配对检验、消融实验、
失败归因)读的都是**逐题字段**,于是结论全错 —— 而且没有任何地方会报错。

**修法不只是改那一行,还要加一道自检:** 出报告前把 summary 和逐题记录对一遍账,
对不上就**拒绝生成报告**。

```python
def _audit_summary(stats, records):
    ...
    if problems:
        raise SystemExit(
            "评估报告自检失败 —— summary 与逐题记录对不上:\n  " + ...
            + "\n\n逐题记录是下游分析的唯一数据源,这里不一致就意味着报告不可信。")
```

统计代码最危险的地方在于:**它错了也不会崩**,只会安静地给出一个看起来很像样的
数字。所以每一条从点估计到结论的路径,都得有东西盯着。

## 六之二、还有一类 bug:它在你的开发机上永远不会出现

上面那个 bug 是**在同一台机器上就能撞到**的。还有一类更阴的。

同一个项目里,给几个仓库接上 CI(ubuntu / windows × 三个 Python 版本)之后,
其中一个红了,而且红得极有规律:

```
Python 3.10  ❌
Python 3.12  ❌
Python 3.14  ✅
```

失败的是这么一条命令:

```
stability-lens check --rule euler --spectrum "-1,-4"
→ error: argument --spectrum: expected one argument
```

在本地(3.14)跑得好好的,换个版本就"参数不对"了?

根因是 CPython 的一个改动。argparse 判断"这个 `-` 开头的东西是选项还是值"时,
只认可**纯负数**字面量(`-1`、`-1.5`)。`-1,-4` 带逗号、`-1+3i` 带 `i`,
两个都不匹配 —— 于是被当成了选项。而在 **Python 3.14 里这个判定被整个删掉了**
(`argparse._negative_number_matcher` 已经不存在),所以同一串参数在 3.14 上就正常。

于是凑成了一个最坏情况:

* 开发机是 3.14 → 测试全绿,一切正常;
* 用户装在 3.10 / 3.12 → 一敲命令就报错;
* **只有"多版本 CI"这一件事能把这两边对上。**

修法本身很简单:在参数进 argparse 之前,把 `--spectrum -1,-4` 改写成
`--spectrum=-1,-4`(等号形式任何版本都认)。真正值得记住的是**发现它的方式** ——
不是靠代码审查,不是靠更聪明,而是靠"在多个环境里都跑过一遍"。

这和你前面读到的是同一条道理:

> 一个指标的可信度,不会超过它的评委。
> **一份报告的可信度,也不会超过你跑过它的环境数量。**

单版本本地开发给出的,是**一个**环境下的绿。它可以很真实,也可以毫无意义 ——
而你从结果上看不出是哪一种。

## 七、一个指标的可信度不会超过它的评委

上面讲的全是"有真值"的情形 —— 求解率、命中率,对了就是对了。

但 LLM 应用的很多指标没有真值:忠实度、答案相关性、有没有幻觉。这些需要一个
评委,通常是 LLM 或者人工。

**在评委本身被评估之前,这些指标报了也没有意义。**

举个具体的:让两个人标注同一批题,报告说"一致率 90%"。听起来不错。但如果
标签分布是 95% 都通过(很常见),把数据摊开看:

| | 原始一致率 | Kappa |
|---|---|---|
| 20 道题,A 全判"通过",B 只在 2 道上判"不通过" | **90%** | **0.00** |

一致率 90%,而 Kappa 精确等于 **0** —— 两个人的判断之间**一点关系都没有**。
那 90% 全部来自"两边都倾向说通过"这个巧合。

所以一条实操规则:

> **报一致率必须同时报 Kappa,并且报出标签分布。**

标签越偏斜,一致率越不可信,而 Kappa 会把它扣回来。

同样的道理适用于任何用 LLM 当评委的场景:先量它的位置偏差、看它和人工的
一致性、看它的置信度校准,然后再谈它给出的分数。**顺序不能反。**

## 八、动手之前,先算要多少样本

最后一条,也是最能体现"评估是设计出来的、不是跑出来的":

**要多少题才能检出 5% 的提升?**

不算这个,你只能回答"越多越好"。

而算了之后你会发现答案强烈依赖于"反向退化"的程度 —— 每改好 1 道题,
同时有多少道题被改坏:

| 退化比 r | 改坏 π01 | 改好 π10 | 分歧率 | 需要题数 |
|---|---|---|---|---|
| 0.00 | 0.0% | 5.0% | 5.0% | **155** |
| 0.25 | 1.2% | 6.2% | 7.5% | 234 |
| 0.50 | 2.5% | 7.5% | 10.0% | 312 |
| 1.00 | 5.0% | 10.0% | 15.0% | **469** |

(基线 70%,α = 0.05,功效 80%)

**注意 r 越大需要越多样本。** 直觉上"改好 5 道、同时改坏 5 道"听起来是扯平了,
实际上它对样本量的要求最高 —— 因为净差异虽然不变,分歧对却翻倍了,差异更难
从噪声里分辨出来。

---

## 九、回到那句话

把上面这些合起来,其实就是一件事:

> **闭环越紧,越可验证,统计就越有用。**

* 有真值的指标(命中率、求解率)→ 配对检验 + 区间 + 校正,立竿见影;
* 需要评委的指标 → **先评估评委**,否则后面全是空中楼阁;
* 评估代码本身 → 也要被测试,而且要有自检。

而如果一件事没有真值、也没法验证,那么再多统计也救不了它 —— 那种时候该做的
不是加指标,是换问题。
